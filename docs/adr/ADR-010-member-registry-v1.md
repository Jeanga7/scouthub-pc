# ADR-010: V1 member registry model

## Status

Accepted for the V1 member registry slice.

## Decision

`Person` remains the canonical human identity. `Account` is optional and only represents a ScoutHub login. A `ScoutProfile` is a one-to-one tenant-owned scouting profile containing the regional `Scout ID` and scouting-specific complementary fields. A `Membership` is a dated organizational attachment and is never replaced in place when a person transfers.

The Scout ID is generated by the PostgreSQL sequence `scout_profile_scout_id_seq` and formatted as `PC-000001`. It is tenant-unique, stable across transfers and independent from insurance numbers or organizational codes. Counting rows is deliberately not used because concurrent creation would create collisions.

At most one territorial membership is active for a person in a tenant. PostgreSQL enforces this with a partial unique index on `(tenant_id, person_id)`. Transfers end the previous row and insert a new row in one transaction. The membership points to the most precise organization node; ancestry is derived from the materialized organization path.

For V1, `Membership.branch` is the explicit source of truth for branch classification. It is nullable where no branch applies or is not yet known. Branches are never inferred from organization names; a future organization configuration slice may introduce a reusable branch catalogue without duplicating values across Person and ScoutProfile.

Appointments remain independent from memberships and continue to describe responsibilities. During V1, RoleAssignment remains the RBAC authority. Member summaries are projection-shaped and omit sensitive profile fields; details are redacted unless `member.read_sensitive` is granted. Scope checks are server-side and use the assignment scope path plus tenant-safe database predicates.

Insurance is kept as profile fields for this slice because annual campaign records are explicitly deferred. A future campaign slice should migrate this to year-scoped records before introducing annual workflows.

## Consequences

- People without an Account can be registered and governed.
- Historical memberships are queryable without inferring past structure from current data.
- Scout IDs consume sequence values on rolled-back transactions; gaps are acceptable and preserve concurrency safety. The format is `PC-` followed by at least six digits, so the sequence has no artificial six-digit ceiling.
- Parent portals, invitations, campaign processing and advanced statistics remain outside this slice.
